# QR-based door access control for event check-in

This change adds a full QR access control flow: when a guest RSVPs, a UUID-based QR code is generated and stored alongside the RSVP. The guest can view their QR ticket at `/mi-entrada/[code]`. At the door, a separate `/scanner` page (PIN-gated, using the device camera) reads QR codes and hits `/api/scan` to mark attendance. The admin panel gains confirmed/entered/pending counters and a link to the scanner.

Watch for: The `/api/scan` endpoint has no rate limiting and no brute-force protection on the PIN (confirmed). The scanner PIN defaults to `1234` and is validated per-scan against a single env var with no lockout, making it trivially brutable in production (confirmed). There is a broken link in the admin panel pointing to `/admin/events/${id}/puerta` which uses the old `/api/checkin` endpoint — scanning new-style QR codes through that path will always 404 (confirmed).

## High-level view

The QR lifecycle runs through three layers: RSVP creation mints a UUIDv4, the guest-facing page renders it as an SVG QR code via `qrcode.react`, and the scanner page reads it with `html5-qrcode` then POSTs to `/api/scan`. The scan endpoint validates a 4-digit PIN from environment, looks up the RSVP by the unique QR code, and flips `attended` to true. Re-scans are detected and surfaced as alerts (success: false) rather than error status codes — the operator sees a warning but no HTTP error.

The security model is thin by design: a single shared PIN protects the scan endpoint, with no per-operator identity, no attempt counter, no rate limiter, and no audit trail beyond the `attended` boolean. The response differentiates PIN failures (401) from unknown QR codes (404), which means an attacker who discovers the PIN can then enumerate codes.

The admin panel now has two incompatible scanner paths: the new `/scanner` (public, PIN-protected, looks up by `qrCode` field) and the pre-existing `/admin/events/[id]/puerta` (admin-session-protected, looks up by RSVP `id` field). The admin page's new "Abrir Scanner de Puerta" link routes to the old path, which cannot resolve the UUID-based QR codes this feature generates.

1. **No rate limiting on `/api/scan`** — The endpoint accepts unlimited requests. Add the same `rateLimit` wrapper used in `/api/rsvp`, keyed on IP, to prevent brute-force PIN guessing and QR code enumeration.
2. **PIN brute-force with no lockout** — A 4-digit numeric PIN has 10,000 combinations and can be exhausted in seconds without rate limiting. Either increase PIN complexity, add a lockout after N failures, or add rate limiting.

Either update the puerta page to use `/api/scan`, or route the admin link to `/scanner`.
4. **Scanner cleanup race** — When `scanning` flips back to `true` (after result dismissal), the effect creates a new `Html5QrcodeScanner` before the previous `.clear()` promise resolves. If the browser hasn't released the camera, the new scanner may fail silently on mobile.
5. **QR entry page accessible without authentication** — `/mi-entrada/[code]` exposes guest name, event title, date, and guest count to anyone with the UUID. UUIDs are unguessable but are transmitted in plaintext via the RSVP response and the URL. If the link leaks (shared screenshot, browser history), the data is exposed.

## Scan endpoint: no rate limiting and weak PIN model

`/api/scan` is the only endpoint in this codebase that handles authentication-like validation (the PIN check) without the `rateLimit` wrapper that protects `/api/rsvp`. The PIN is compared directly against `process.env.SCANNER_PIN || "1234"`. An attacker can enumerate all 10,000 combinations of a 4-digit PIN with trivial scripting. The response differentiates "PIN incorrecto" (401) from "QR no encontrado" (404), which means an attacker can first discover the PIN and then enumerate QR codes.

The fix is straightforward: wrap the endpoint with the existing `rateLimit` utility, keyed on IP, with a tight window (e.g., 10 attempts per minute). A lockout or exponential backoff after repeated 401s would further harden it.

## Dual scanner paths: `/scanner` vs `/admin/events/[id]/puerta`

This diff introduces `/scanner` (a public page gated only by the PIN) and also adds a "Abrir Scanner de Puerta" link in the admin event detail page that points to `/admin/events/${id}/puerta`. The puerta page is pre-existing code that calls `/api/checkin` with `{ rsvpId: decodedText }` — it expects to scan the RSVP record's `id` field. But the QR codes generated by the new RSVP flow encode the `qrCode` UUID field, not the `id`.

If an operator opens the admin panel, clicks "Abrir Scanner de Puerta", and scans a guest's QR code, the checkin API will look up by `id`, fail to find the RSVP, and return a 404 error. The two scanner flows are incompatible in their lookup keys.

The options are: update the puerta page to use `/api/scan` (with PIN embedded or removed since it's already behind admin auth), remove the link in favor of `/scanner`, or change the puerta scanner to look up by `qrCode` instead of `id`.

## Scanner lifecycle and camera release

The scanner page's `useEffect` depends on `[pinVerified, scanning, pin]`. When a scan result is dismissed and `setScanning(true)` is called, the effect fires and creates a new `Html5QrcodeScanner` instance. However, the previous scanner's `.clear()` is invoked in the cleanup function of the *prior* effect invocation, and it returns a promise. If the browser hasn't finished releasing the camera stream by the time the new scanner calls `render()`, the new instance may fail to acquire the camera.

On mobile devices (the primary use case for a door scanner), camera release can take 100-500ms. The `scannerRef.current` guard prevents double-initialization within a single effect cycle, but doesn't prevent the race between cleanup of cycle N and initialization of cycle N+1. A small delay or an explicit "ready" state after cleanup would close this gap.

## Guest entry page exposure

`/mi-entrada/[code]` renders guest name, event title, event date, and party size to anyone who has the URL. The UUID is cryptographically random (UUIDv4), so enumeration is infeasible. The exposure risk is limited to scenarios where the URL leaks: shared screenshots, browser history on shared devices, or HTTP referrer headers if the page ever links externally. Additionally, `notFound` is imported but unused — the page renders its own inline "not found" UI instead of calling the Next.js function.
